# 后续路线图

以下是当前版本**尚未实现**的方向，不承诺日期。它们不得被当作现有 API、数据结构或测试脚本；当前范围以 [系统架构](architecture.md)、[HTTP API 业务语义](api.md) 和[阅读工作区设计规格](superpowers/specs/2026-08-21-reading-workspace-annotations-model-profiles-design.md)为准。

| 方向 | 进入条件 | 架构后果 |
| --- | --- | --- |
| OCR | 已确认扫描件/图片 PDF 是核心使用场景，并定义可审计的文字与坐标质量标准。 | 引入 OCR 阶段、页图像/文字来源与置信度；TextLayer 选区、可选论文位置链接和 OCR 文字来源需要明确区分。 |
| 多用户 / 多租户 | 已有认证、授权、工作区和数据隔离的产品需求，并确定租户生命周期。 | `paper_id` 所有权扩展为用户/工作区/租户范围；模型密钥、会话、请求幂等、存储路径和删除恢复都需加入租户边界；单进程锁不足以提供隔离。 |
| 云同步 / 协作 | 已定义冲突处理、共享权限、离线行为和服务端数据归属。 | SQLite 本地事实源需演进为同步协议或服务端存储；笔记/高亮需版本或 CRDT/冲突策略，模型密钥不能随内容同步，删除需区分个人删除与共享回收。 |
| 跨页选区 | 已确定跨页引用的用户体验、文本连续性和页面渲染规则。 | 单个锚点的 `page_number` 与单页矩形集合需演进为多页片段；PDF.js 采集、锚点哈希、批注叠层、笔记检索和引用响应均需新 schema 与迁移。 |

在任何一项进入实施前，先写 ADR、更新数据模型与 API 契约，并为迁移、并发和删除行为补充确定性测试。不要通过临时字段或未记录的前端状态提前实现这些能力。
